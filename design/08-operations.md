# 08 运行与审计

对应流程第 9 步「控制与运行」。

## 运行目标

| 指标 | 目标 |
| --- | --- |
| 月成本（服务器 + 模型调用） | ≤ 1000 元 |
| 首字响应时间（第一句通过校验的规则结论） | P95 ≤ 2 秒 |
| 完整回答时间 | P95 ≤ 15 秒 |
| 可用性 | 99.5%（每月停机不超过约 3.6 小时） |
| 每账号每日提问 | 100 次 |

单台服务器做到 99.5% 是可行的，前提是有每日备份和半小时内能恢复的部署脚本。

## 容量估算

| 项 | 估算 | 依据 |
| --- | --- | --- |
| 块数 | 入库后实测 | 只统计 `src-srd51-zh`，见 [02-sources.md](02-sources.md) |
| 向量存储 | 约 100–250 MB | 2 万块 × 1024 维 × 4 字节约 80 MB；3072 维约 240 MB，加 HNSW 索引 |
| 嵌入模型内存 | 服务器不常驻 | 选型记录二只比较 API，查询和全量嵌入都走接口 |
| 服务器规格建议 | 4 核 8 GB | 应用与 PostgreSQL 共用 |
| 峰值请求 | 每秒 1–2 个 | 小规模设计；实际并发受模型 API 的速率限制约束 |

## 成本估算

单题里哪些段落会计费，先分开记。父节正文和更早的用户原话各送多少 token，由 [07-pipelines.md](07-pipelines.md) 的实验档位决定，不预设 4000 token 或固定轮数。引用校验失败时重新生成，按 10% 的比例估计。

若厂商把输入分成缓存命中和未命中，账单按三项记：命中的输入、未命中的输入、输出。系统提示词放在最前并保持不变，才可能按命中计。父节正文每次不同，按未命中估。重排若另有费用，单独加一行。闲置摘要的等待时间默认 30 分钟，每用户同时有效的 API 密钥默认最多 2 把，两者都是可配置项。闲置摘要计入全站费用，不占用户提问次数。空问题和超长问题不占每日次数，也不占每分钟次数。档位选定后，用厂商返回的 token 数重算单题成本。2026-11-06 已选定 `qwen3.7-flash-2026-07-15`。下面第一行是 `runs/2026-11-06-02` 的实测：19 题合计 0.017707 元，约 0.00093 元/题。单价是华北2（北京）、输入不超过 3.2 万 token 的官网价。高价一行仍是示意，本轮没有选用旗舰：

| 情况 | 输入单价（元/百万 token） | 输出单价（元/百万 token） | 单题成本 |
| --- | --- | --- | --- |
| 千问 `qwen3.7-flash-2026-07-15` | 0.2 | 0.8 | 约 0.00093 元 |
| 高价模型（示意，未选用） | 20 | 80 | 约 0.17 元 |

月度预算拆分：服务器约 300 元（示意，按实际报价调整），备份与监控约 50 元，模型调用约 650 元，折合每天约 21 元。

- 用已选定的千问，每天约可回答 2.3 万题。
- 用上表的高价示意模型，每天约可回答 120 题。

由此得到两条约束：

1. **真正控制成本的是全站每日上限。** 每账号每日 100 次只是单个账号的上限，十几个重度用户就能用满全站额度。全站每日模型费用上限先设为 21 元，达到 80% 时告警，达到 100% 时暂停新提问。
2. **选型记录三要把单题成本作为硬指标。** 高价模型在这个预算下只能支撑很小的用量。

## 审计字段

每次请求写一条审计记录：

| 字段 | 说明 |
| --- | --- |
| `request_id` | 请求编号 |
| `user_id` | 假名编号，不记录邮箱或 GitHub 用户名 |
| `created_at` | 时间 |
| `question` | 问题原文（用于审核与评估） |
| `lang`、`detected_version` | 提问语言、识别出的版本意图 |
| `result_type`、`refusal_class` | 回答或拒答，以及拒答类别 |
| `retrieved` | 检索到的 `entry_id` 列表与相似度 |
| `cited` | 回答实际引用的 `entry_id` 列表 |
| `citation_check` | 通过、重试后通过、失败 |
| `index_version`、`prompt_version`、`model_id`、`guard_version` | 发布与回退的追溯依据 |
| `tokens_in`、`tokens_out`、`cost_estimate` | 成本 |
| `latency_ms` | 分阶段耗时：检查、检索、首字、完整回答 |
| `feedback` | 好评、差评、备注（事后补写） |

管理操作单独记一条审计：谁、何时、做了什么（接入或停用来源、发布或回退、调整配额）。

## 脱敏与保留

- 日志和审计里不记录令牌、邮箱、GitHub 用户名、IP 地址明文。IP 只保留用于限流的哈希值，保留 7 天。
- 问题原文可能含有用户自己写入的个人信息。审核员只能看到与审核队列关联的请求。
- 保留期限：

  | 数据 | 保留期限 |
  | --- | --- |
  | 请求审计 | 90 天 |
  | 管理操作审计 | 1 年 |
  | 聚合指标 | 长期 |
  | 会话 JWT 拒绝名单 | 保留到该令牌的 `exp`，最长 8 小时 |

- **删除一条对话：** 立刻删除该对话的存档、会话卡片和摘要，并作废对应的 `conversation_id`。已经写下的审计记录不删，仍保留 90 天，供滥用排查和每周抽样。审计不通过 API 提供。
- **注销账号：** 30 天内删除其账号信息和所有请求审计，包括问题原文；聚合指标不含个人标识，不删除。

## 备用路径

- **第一期：** 模型不可用时返回 503，不计入配额。
- **第三期：** 加入备用模型。主模型连续失败 3 次或 P95 首字响应超过 5 秒时，切到备用模型。备用模型同样要先通过验收题。

## 告警条件

| 告警 | 条件 | 接收人 |
| --- | --- | --- |
| 成本 | 全站当日模型费用达到上限的 80% | 管理员 |
| 错误率 | 5 分钟内 5xx 比例 > 5% | 管理员 |
| 延迟 | 1 小时内首字响应 P95 > 3 秒 | 管理员 |
| 引用校验失败率 | 1 天内 > 5% | 管理员 |
| 拒答率突变 | 本周拒答率比上周变化超过 10 个百分点 | 管理员 |
| 索引落后 | 官方 SRD 页面或上游仓库有新版本，超过 30 天未接入 | 管理员 |
| 下架时限 | 下架请求超过 5 天未完成 | 管理员 |

第一期告警通过邮件发送，告警渠道的凭据从环境变量读取。

## 发布与回退

带版本的对象：`index_version`、`prompt_version`、`model_id`、`guard_version`，以及验收题集版本 `eval_version`。

发布步骤：

1. 在构建环境里跑全部验收题（含放行题），达到门槛并由项目作者签字。
2. **灰度：** 按 `user_id` 哈希取 10% 的用户使用新配置，持续 24 小时。比较新旧配置的引用校验失败率、拒答率和差评率。
3. 指标没有变差，就切换全部流量。
4. **回退：** 把已发布指针切回上一个版本，目标 5 分钟内完成。旧索引版本保留到下一次发布成功。

第一期手动执行以上步骤；第二期把第 1 步做成发布门禁，自动执行。

## 线上抽样评估

- **第一期：** 每周人工翻看 20 条请求。
- **第三期起：**
  - 每周随机抽 50 条线上问答自动打分，其中 10 条人工复核；
  - 持续观察拒答率、无证据率、引用校验失败率的周变化；
  - 抽到的典型问题经审核后补进验收题集，升级 `eval_version`。

## 反馈处理流程

进入审核队列的来源：

- R1、R2、R4 类拒答；
- 用户差评；
- 引用不一致的自动提交；
- 抽查发现的译文问题；
- 待审核的术语。

处理要求：

- 审核员在 7 天内处理每一条。
- 每条的处理结果落到以下三处之一：

  | 处理结果 | 执行人 |
  | --- | --- |
  | 修正源数据：术语表，或标记有问题的译文条目 | 审核员提出，管理员执行重建 |
  | 加进验收题 | 审核员起草，管理员升级 `eval_version` |
  | 调整检索或提示词 | 管理员，走发布流程 |

- 第一期审核队列只在管理端以列表形式展示，由管理员兼任审核员；第二期上线审核员角色和独立的队列页面。
